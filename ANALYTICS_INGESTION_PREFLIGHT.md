## Executable batch boundary

prepareEventBatch accepts a raw JSON string, trusted server publication context and server receive time. It enforces UTF8 size<=16KiB,1..20 events, strict PR5.107 event parsing, canonical UTC times no more than24h old or5min in the future, current published-product membership, and exact server-qualified route/product/position for route impressions/clicks. Product-page events require public product identity but no route placement. Exact retry IDs deduplicate; conflicting payload reuse rejects the batch atomically before storage. Return includes trusted receive timestamp distinct from client action time.

PublicationContext must be constructed by future server code from current public products and actual eligible route ranking (not raw memberships). It must never be accepted from request JSON. Invalid client fields cannot claim publication. Context freshness, durable uniqueness across requests, rate limits and actual human/browser attribution are not supplied by a pure function. A changed position rejects rather than silently attributing to an incorrect placement; producers/collector must later define rendered-list version handling and track rejection diagnostics to avoid biased CTR. Late events outside24h are deliberately rejected; dashboards need an ingestion cutoff before interpreting incomplete windows.

The16KiB check happens after this pure function receives a string; the future HTTP endpoint must separately cap bytes while reading the stream and reject invalid content types/origins before constructing the body. It also needs bounded batch validation, site-origin checks, durable quotas, authoritative publication lookup, ingestion timestamps and persistence. No claim of deployed abuse protection is made here.
